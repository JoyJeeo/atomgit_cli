## D01 默认总时限与实际执行不一致

- 原问题 ID: `UPLOAD-01`
- 状态: `accepted`
- 证据: CLI 默认输出显示“上传总时限不限”，但默认请求超时 300 秒继续作为
  `upload_timeout` 传入 resumable 实现，并据此建立 300 秒总截止时间。
- 影响: 用户看到的超时合同与实际执行不一致，长时间上传可能被提前终止。
- 约束: 上传总时间不设限；保留请求等待超时、有限重试、故障退出、Ctrl+C 清理和断点
  恢复。CLI/SDK 同义，原有请求阶段覆盖、全局状态恢复、凭证和源文件安全不退化。
- 备选方案: 修改提示以承认默认总时限 300 秒；仅修默认值并保留显式总时限；
  全面取消上传总时限，仅保留请求等待超时。
- 方案权衡: 修改提示会保留对正常长上传的错误限制；仅修默认值不符合维护者后来
  确认的无总时限方向；全面取消总时限符合目标，但显式参数的旧行为发生兼容变化。
- AI 推荐: 全面取消总计时，在共享上传服务、子进程等待和恢复链路去掉由请求值派生
  的截止时间；不新增计时器、看门狗或依赖，也不再需要全链路 `None` 改造。
- 已确认行为: 省略 `--timeout` 时默认请求等待 300 秒；显式 N 时请求等待采用 N；
  两者均不限制上传总时间。当前 HF 写入等待 60 秒、部分控制面 min(N,15) 保留，
  不声称所有请求阶段均统一五分钟。
- 兼容变化: CLI 与对应 resumable SDK/API 的显式超时不再终止整次上传；在帮助、FAQ、
  上传分析及受影响 SDK 文档中说明，并同步替换旧总时限契约及补足故障处理证据。
- 验收: 覆盖默认超过 300 秒、显式小超时持续上传、多批累计、请求超时与有限重试、
  取消/进程异常、CLI/SDK 一致性、成功失败后的全局状态与资源恢复；实施后必须通过
  完整离线基线、compileall、pip check、diff check 及独立审查。
- 开放问题: D01 的行为方向无待确认项；D01 确认时 D02/D03 尚未决定，后续决定见
  各自章节。请求超时不能覆盖所有内部死锁，受控远程行为尚未验证。

## D08 状态不明时重跑存在重复提交风险

- 原问题 ID: `LFS-04`
- 状态: `accepted`
- 证据: pointer 确认失败发生在远端提交之后，而 HF metadata 尚未标记 committed；

- 影响: 重跑可能重复提交相同路径、产生无意义历史；目标分支已被他人推进时，还可能

  所有输出继续脱敏。
- 备选方案: 继续依赖本地 `is_committed`；重跑后直接比较当前分支并覆盖不一致项；
  或在远端写入前持久化私有提交凭据，重跑先对账不可变 revision，并用
  `parent_commit` 阻止并发覆盖。

## D10 上传与监控进程缺少完整数据合同

- 原问题 ID: `MON-02`
- 状态: `accepted`
- 证据: CLI 在父进程创建 `UploadSession` 和后台 `SnapshotPublisher`，
  然后 resumable 适配器另建子进程执行 HF worker。现有
  `set_upload_observer(lambda ...)` 只是进程内全局回调：`fork` 会让子进程
  继承一份 `UploadSession` 副本并直接写快照，父进程发布器又会用旧
  副本覆盖；`spawn` / `forkserver` 不继承该回调，状态可完全丢失。
  父进程当前在 `process.join()` 中阻塞，只有一条上传结果队列，没有运行
  期间的结构化状态通道。monitor 是独立进程，只能读 JSON 快照，无法
  修复这个缺口。
- 影响: 上传端即使拥有实时状态，独立 monitor 也无法可靠重建。
- 约束: 父进程必须是会话状态和 JSON 快照的唯一写入者；子进程不得
  继承或持有 `UploadSession`、publisher 线程、文件路径或父进程 callback。观测
  不得阻塞上传，也不得与成功/失败结果、取消和子进程清理共用同一
  可被状态洪水阻塞的通道。传输字段继承 D09 的白名单、脱敏、有界和幂等
  合同；公开 CLI/SDK、HF 上传、慢流策略和 monitor 只读语义不变。
- 备选方案: 子进程继续直接写 JSON；使用 `multiprocessing.Manager`
  共享字典；把状态和结果混在现有队列；或使用一条独立、有界、显式传入
  子进程的观测队列，父进程在等待子进程时持续排空并归并。
- 方案权衡: 子进程直写无法消除多写者覆盖，且 `spawn` 仍需要新通路；
  `Manager` 额外启动服务进程并让热路径跨进程同步；混合队列会让可丢弃的
  显示采样威胁必须可靠送达的上传结果。独立队列只需复用标准库，边界
  最小，并且能明确分离“观测可降级”与“上传结果必须正确”。
- AI 推荐: 保留现有独立 `result_queue`，另建最多 256 条的
  `observation_queue`。子进程通过 `put_nowait` 发送完整最新状态或关键事件；
  队列满、序列化或发送失败时丢弃当前观测消息，不等待、不重试。因为
  `flow_state` 是完整覆盖值，丢失中间样本可被下一份状态自愈；关键结论同时
  存在最新状态中，事件历史不作上传成功证据。
- 消息合同: 内部 envelope 固定为 v1，只允许 `flow_state` 和
  `flow_event`，包含正整数 `sequence`、子进程内匿名 `flow_key` 及 D09
  白名单 payload。不携带 session ID、仓库、路径、OID、URL、token 或异常
  原文。每次 resumable 子进程由父进程分配不持久化的私有 `source_id`，把
  `(source_id, flow_key)` 映射为会话内唯一的 `Flow-01` 等编号；父进程按序号拒绝重复
  或迟到状态，未知版本/类型/字段整条丢弃。
- 运行合同: 子进程启动后首先清除可能由 `fork` 继承的父进程
  observer，再把新协调器的结构化输出发送到明确传入的队列。父进程用
  短周期 `join(timeout)` 与队列排空循环取代一次无期限 `join()`；每条合法消息
  只在父进程调用 D09 的 `UploadSession` 结构化入口。子进程退出后父进程
  先排空已成功入队的状态，再处理结果；根据已确认的成功、失败、崩溃或
  取消，父进程用固定安全原因收敛当前批次仍活跃的 Flow，不伪造未注册
  的 Flow，不改变原有结果分类或异常。
- 可观察验收: 同一受控上传在 `fork`、`spawn`和可用时的
  `forkserver` 下均由父进程得到同义、同序、脱敏的状态；子进程不写快照，
  父进程旧状态不会覆盖子进程新状态。队列满、callback 抛错、非法消息、快照
  不可写、子进程无结果/崩溃及 Ctrl+C 均不改变上传结果、退出码、子进程
  清理和断点元数据；状态队列洪水不得阻塞结果送达。
- 实施与测试边界: 建议与 D09 在同一开发 Issue 中作为不可分割的相邻

  台账；不新增生产模块、依赖、公开参数或测试脚本。扩展

  `UPO-005` 和一条跨平台进程不变量；实际 ID 和计数以实施时台账为准。
