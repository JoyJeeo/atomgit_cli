# 常见问题

## 开发时应该使用哪个分支？

使用 `main`，它是唯一开发和发布主线，跟踪 `github/main`；唯一代码远程为 GitHub。详见
[main_branch.md](main_branch.md)。

## 为什么所有命令都要求激活 conda 环境？

项目依赖锁定的 `huggingface-hub==1.1.7` 和 `datasets==4.4.1`。不同环境中的
函数签名可能不同，错误环境会导致测试结果和用户行为不一致。

```bash
source "$(conda info --base)/etc/profile.d/conda.sh"
conda activate atomgit_cli
```

## 普通用户怎样安装 CLI？

使用 `install.sh` 从已完成 GitHub Release 下载并校验 wheel；不要求 conda，可用
`--python` 指定目标 Python。Windows 使用固定 Release wheel 和 `SHA256SUMS` 手工
安装；POSIX/macOS/Linux 才支持 `install.sh`。

## CLI 是怎样开发安装出来的？

`setup.py` 注册 `atomgit=atomgit.cli:cli`。执行 `python -m pip install -e .`
后，当前 conda 环境会生成 `atomgit` 命令。

## CLI 和 SDK 是同一套实现吗？

不是。CLI 主要走 `cli/__init__.py -> api/__init__.py`，Python SDK 通过历史 `atomgit_hub.py`
facade 进入 `atomgit.sdk`。它们
共享配置，但上传、下载和错误处理存在平行实现，因此修改公共能力时必须检查
两侧是否产生行为漂移。

## token 保存在哪里？

默认保存在 `~/.atomgit/config.json`。不要把该文件内容复制到日志、Issue、
测试夹具或提交中。

## 登录为什么会修改 Git 配置？

登录成功后，CLI 会为 `atomgit.com` 和 `hub.atomgit.com` 注册全局 Git
credential helper，使 Git HTTPS 操作能够复用保存的 token。因为它会修改用户
全局状态，自动化测试默认不应在真实 HOME 下执行。登录期间，这两个域名会用
空 helper 条目重置继承的通用 helper 链，避免 token 被系统 keychain 等其他
helper 再次保存。原有的域名专属 helper 值会原样保存到权限受限状态文件，但
不会写入本次登录 token，并在 logout 时按原顺序恢复；其他域名不受影响。
如果恢复失败，logout 会返回非零；解决 Git 配置问题后可再次执行 logout，CLI
会根据残留状态文件重试恢复，即使当前已经显示为未登录。

Git helper 使用登录时已验证并缓存的用户名，不会在每次 Git 操作时调用身份
API。从旧版本升级后应重新运行一次 `atomgit login`；如果本地配置缺少 username，
helper 会拒绝返回 token。

## 未登录可以下载吗？

CLI 允许尝试下载公开仓库。私有仓库需要有效 token。是否真正匿名可访问仍取决
于仓库权限和 AtomGit 服务端响应。2026-08-04 的受控矩阵确认同一版本客户端可
匿名下载公开测试仓库；对私有仓库匿名请求失败，提供 token 后下载和 SHA-256
回读成功。

## resumable 当前是否可用？

可以。当前实现通过
`HfApi(endpoint="https://hub.atomgit.com", token=...)` 固定 AtomGit 端点并
完成认证，不再把不兼容的 `token` 参数传给 `upload_large_folder()`。2026-08-04
分别对私有 model 和 dataset 使用
399,300,506 字节文件执行了 CLI 超时中断、同目录续传、下载回读；两者最终
SHA-256 均一致。dataset 的用户类型保持不变，底层自动使用共享 model 兼容路由。
dataset 中的 `.arrow` / `.parquet` 不再显示 HF 1.1.7 因该映射产生的
model 仓库误报警；真正的 model 上传和其他警告不受影响。
CLI 目录上传现在默认选择 resumable；`--path-in-repo` 通过稳定的本地投影表达
远端前缀并保留 HF 元数据。需要单一提交说明或普通目录上传时使用 `--message`
（未显式选模式时自动普通上传）或 `--no-resumable`。

resumable 只上传到已存在的仓库。CLI 在所有批次前执行一次只读仓库/revision
校验，并屏蔽 HF 1.1.7 large-folder 启动阶段的隐式建仓请求；创建仓库仍需显式
使用 `atomgit repo create`。如果仓库策略把超过 1 GB 的文件判定为普通 Git 文件，
CLI 会在提交读取和 Base64 编码前停止，提示在 `.gitattributes` 中配置 Git LFS。
默认行为不会修改仓库；错误提示会说明可以在明确授权配置提交时加
`--auto-configure-lfs`。启用后 CLI 会为服务端判定为 LFS 的安全扩展名显示
`*.扩展名` 规则及其全仓库影响，并在 LFS 对象上传或引用提交前检查根目录
`.gitattributes`。缺少有效规则时，它在私有缓冲目录保留已有字节并追加标准 LFS
行，携带目标 revision 当前 commit 做并发保护，只提交该文件并验证远端内容，再
重试当前批次；同一命令内已确认的扩展名不会跨批重复检查。对于超过 1 GB 却被服务端
判定为 regular 的文件，该选项仍会补齐规则并刷新模式。未提交断点若缓存了旧的
regular 模式，也会在规则确认后清除旧模式并重新判定。规则无法安全推导、权限失败、
并发冲突无法确认或配置后仍被判定为 regular 时会停止，不会生成宽泛规则或无限配置
commit。已有哈希和已提交状态会保留。
该主动路径已在授权测试仓库完成“缺失规则追加并上传、不可变 commit 回读、相同命令
重跑不产生新提交”的真实验收。

## 为什么预上传完成后仍可能失败，怎样查看原因？

LFS 预上传只表示对象传输阶段完成，不表示文件引用已成功提交。
resumable 失败提示会显示可获得的最后已知阶段、白名单异常类型、HTTP 状态码和
子进程退出码。每次 LFS 预上传重试及最终失败还会显示可获得的请求方法、
域名、请求类别、异常链和系统连接错误码。异常链中的未知类型会脱敏，
不会覆盖链上已识别出的连接、DNS、TLS 或超时异常；没有相关证据的字段不显示。
域名只显示内置白名单中的服务地址（包括 `hub.atomgit.com`、`hub.gitcode.com`），
其他地址显示 `other`；不输出路径、查询参数、
请求头或响应正文。`lfs_batch` 表示 LFS 协商，`object_upload` 表示 PUT 上传请求，
`lfs_verify` 表示校验请求，未识别的请求类别显示 `http`。
这些日志用于定位失败请求，不据此推断代理、网络或平台的责任。
子进程未返回结果、结果格式异常或非正常退出会分类为“上传进程异常”，
不会据此宣称服务端失败或远端没有提交。阶段通过独立观测队列尽力传递；队列不可用
或消息丢失时阶段可能为未知，不影响上传结果判断。

上传期间，HF/HTTP 依赖日志使用固定脱敏提示，后台线程异常仅显示安全类型；
不打印原始异常、认证参数、签名 URL 或响应正文，调试日志同样受保护。
resumable 上传在 stdout/stderr 都连接交互终端时显示 LFS 逐文件动态进度。
持续传输期间，字节数、速度和剩余时间按独立的约 1 秒采样更新；这不改变
5 秒 Flow 观测或 30 秒慢速判断窗口。刷新由上传读取下一块数据触发，网络写入
阻塞时可能延后，不会虚增已传输字节。批次汇总报告仍约每 60 秒输出一次。

普通日志通过同一个输出管理器让出并重绘进度区，保留历史记录。若任一输出被重定向，
逐文件状态改为约每 10 秒追加一次；开始与终态立即记录。仍停用 tqdm 后台监控。
`--no-progress-bar` 同时关闭逐文件进度和每 60 秒的批次报告，
保留批次、重试、错误和最终汇总。100% 不等于提交成功。
这些进程级日志和线程处理钩子在上传结束后恢复；同时发生的依赖日志也会被脱敏。

断点元数据会保留；重新执行相同命令时继续使用有效哈希和已预上传状态。
如存在待确认提交，先按已有记录核对远端，不能根据本地“确认 0”断定远端没有写入。
不要为了重试删除缓存。默认并发和单次请求超时不变。

## 单个文件失败会中止整个目录上传吗？

resumable 上传按文件隔离失败。网络错误、502/503、超时和限流每轮最多尝试三次，
仍失败就保留断点、让出位置，并在队尾等待下一轮三次尝试；累计失败次数没有上限。
其他文件继续传输，准备好的文件在有空闲 worker 时优先逐个提交；未完成的批次轮转
补传，不阻断后续批次。只有所有选中文件均确认提交后，整个命令才返回成功。

失败计数、补传轮数、最近安全诊断及下次尝试时间保存在投影缓存的
`retry-state-v1.json` 中。短重试采用退避，轮次等待最高 300 秒；服务端
`Retry-After` 更长时按服务端要求等待，429 冷却也限制后续批次。
未知错误、源文件暂时不可读或服务端排除的选中文件进入“异常待处理”，定期重新检查；
仅在实际失败时打印一次详细日志，终端用黄色/红色标识，重定向时保留文字标签。
日志包含文件/批次、失败阶段、本轮及累计次数、已识别原因、脱敏诊断和下一步动作。
未知原因明确标注未识别，不输出原始异常正文、令牌或签名 URL。等待和冷却期间
不重复打印异常汇总；再次尝试又失败时才产生新的失败日志。
加入候补和开始补传时立即输出整个任务的候补、正在补传及异常待处理数量。
这些文件不会被当作已完成或静默丢弃。未能解决的异常可以一直等待，按 Ctrl+C 停止。

确认的认证/权限/仓库/配额错误、损坏的关键断点、无法安全处理的提交冲突或上传进程
异常会停止任务。临时网络故障不会仅因重复次数多而停止；提交响应不确定时先核对
远端状态，再决定是否重新提交。Ctrl+C 保留已保存状态；重新执行同一命令继续。
basic LFS PUT 失败后的对象可能需要从头传输，不保证字节级续传。

跨盘上传时，缓存投影可能通过符号链接指向外置盘上的源文件。提交对账只接受本次
任务明确选中的对应源文件，并检查链接目标、源文件是否被换成链接，以及读取前后的
文件身份、大小和 SHA-256。合法投影可以继续对账；任意链接、被改指向的投影或
内容变化仍会停止后续提交。对账时遇到暂时的源文件读取错误，保留待处理状态并重试。
对账失败日志会区分“投影目标不匹配”“源文件内容变化”和“暂时无法读取”，不会再用
“本次没有创建新提交”否定前面已确认的提交。已有断点可直接复用，无需删除缓存。

## 为什么 CLI 上传的 LFS 文件会让新克隆立即显示 modified？

旧的 AtomGit HF commit 服务会把 `lfsFile` 元数据生成成缺少最终 LF 的 Git LFS
pointer。文件的 LFS OID、大小和实际对象没有变化，但 `git-lfs clean` 会把 pointer
规范化并补上 LF，于是 Git 把刚克隆的文件判定为已修改。

当前 CLI 和 SDK 上传会在客户端生成固定 ASCII/LF 的标准 pointer，同时保留原有
LFS 对象上传；提交完成后再按精确 commit SHA 读取 V5 原始 blob 做逐字节验证。
单文件、普通目录和 resumable 目录统一使用这项契约，不针对某个仓库名称。若服务
返回的 pointer 不规范或无法验证，上传返回失败而不是误报成功。此修复阻止未来
CLI 上传继续引入问题，但不会自动改写既有提交；已有非规范 pointer 需要单独授权
的规范化提交或服务端修复。

如果服务端已经返回合法 commit SHA，但上述只读验证仍失败，CLI 会区分为“远端提交
已创建、本地确认失败”，隐藏 SHA，并提示先检查远端再决定是否重试；这避免在状态
不明确时重复创建提交。三次确认耗尽后，提示还会区分最后一次失败属于认证、权限、
未找到、限流、服务、超时、连接、请求、响应或内容不匹配；不会显示 URL、响应正文、
仓库路径、OID、token 或 SHA。原生 SDK 的失败结果会把两个状态、经校验的 revision
和 `confirmation_failure` 原因码放在 metadata 中，历史 SDK 则抛出仍可被
`CanonicalLfsPointerError` 捕获的细分异常。

## 为什么普通大目录上传会警告并长时间没有进度？

`--no-resumable` 使用锁定 `huggingface-hub==1.1.7` 的 `upload_folder`。该版本在
应用 ignore patterns 后超过 30 个文件时提示大目录上传，超过 200 个文件时使用
warning 级别。提示不是失败，也不是根据总字节数触发；随后客户端会先读取并计算
全部待上传文件的哈希，因此真正的网络上传进度可能很久以后才出现。

普通模式直接读取源目录，不建立 `~/.cache/atomgit/upload-projections/` 完整
投影；LFS 文件默认最多使用 5 个线程并行上传。它会通过内容哈希询问服务端，已
存在的完整 LFS 内容只需在新提交中引用，因此相同文件换一个仓库内目录后可能
近乎立即完成。这是服务端内容去重，不是本地断点续传；传输到一半的单个新文件
仍可能需要从头重传。

一次处理数百或数千个文件可能在全部哈希和 LFS 传输之后，才因最终提交过大或
网络问题失败。当前 CLI 会在程序内部按 20 个实际上传文件顺序分批，失败后重新
执行同一命令即可继续使用稳定的批次投影；不会修改源目录，也不要同时运行多个
大目录上传进程争抢磁盘、网络和同一仓库分支。

CLI 会先应用 `--ignore` 再打印文件数量和大小，因此该数字与实际上传集合一致。
双引号已经阻止 shell 展开通配符，不要写成 `\*\*`；CLI 会在远端调用前拒绝
这种写法。递归忽略隐藏内容、JSON 和 `output` 前缀内容应写为：

```bash
--ignore ".*,**/.*,*.json,**/*.json,output*,**/output*"
```

上传总时长始终不限；`--timeout` 仅控制默认网络请求等待，省略时为 300 秒。
LFS pointer 确认使用同一个请求超时；HF 写入等待仍为 60 秒。
写入超时会提示检查网络或降低并发，不会建议通过增大 `--timeout` 改变写入等待。
显式超时不再用来终止整次上传；持续正常传输的请求可以超过这个等待阈值。
resumable 收到 429 时遵循 `Retry-After` 或退避等待，不因累计失败次数终止。
临时失败的文件每轮尝试三次，之后进入候补队列轮转；可上传的文件独立提交。
入队日志显示整个任务的“当前候补 / 正在补传 / 异常待处理”，按文件去重，
候补数不包含正在补传、首轮前两次重试等待中的文件或尚未尝试的文件。
前两次失败显示“本轮重试”，第三次显示“加入候补”；异常待处理单独统计。
重启后按同一命令的批次、当前所选文件和有效断点重建，已确认提交的文件不计入。

开始补传会提示复用哈希、尝试复用已上传对象，或重新传输内容。basic LFS 没有
文件内字节续传保证，未完成的 PUT 从头传输；服务端对象过期也可能需要重传。
`resumable` 表示文件级恢复，不代表服务端一定支持 multipart。
若远端提交结果不明确，CLI 保留私有待对账记录，重跑时先核对不可变 revision，
匹配内容只恢复本地状态。临时读取故障继续等待；全局认证、额度、内容冲突或不安全
的恢复状态仍会停止，并保留此前已确认的提交。不要先清除缓存，否则会失去断点保护。

如果某个 LFS 对象已有稳定速度基线，之后连续约 90 秒明显落后于自身和健康同伴，
CLI 会先估算继续等待与重建请求的剩余时间。只有重建预计至少快一倍时才只替换该
对象的连接，其他 worker 不暂停。basic LFS 对象必须从零重传；multipart 只重试
当前未确认 part，并保留同一 action 中已确认的 ETag。每个对象最多自动替换三次；
新连接未达到 2 倍改善，或有稳定同伴时未达到同伴基线的 70%，便停止继续替换。
全部连接同时变慢时最多允许一个探针。因此首次就慢、
缺少可信基线或剩余数据很少的对象可能继续当前连接，这是为避免无收益重传和重连
风暴而保留的限制。网络或服务端响应不明确仍通过新的 LFS Batch 查询对账，而不是
直接在旧签名 URL 上重复 PUT。

## 长时间上传时可以锁屏或熄灭显示器吗？

显示器熄灭或锁屏不会终止终端进程，只要操作系统仍保持唤醒，上传就会继续。
整机睡眠、合盖睡眠、关机、关闭承载上传的终端或断开源磁盘会暂停或终止网络与
文件读取。macOS 可在另一个保持开启的终端中使用
`caffeinate -i -w <上传进程 PID>`，仅在对应上传进程存活期间阻止空闲系统睡眠；
它不保证阻止合盖、手动睡眠、关机或电量耗尽。

## 下载和上传的 `--revision` 有什么区别？

整仓和单文件下载均支持 `--revision` 指定分支、标签或提交；未指定时查询仓库
默认分支，查询失败不会猜测为 `main`。`download REPO FILE` 与 `download-file`
使用相同规则，`-r` 仍表示仓库类型。切换分支时不要使用旧分支的 manifest 清理文件。

CLI 和原生 `AtomGitClient` 上传支持已存在且通过验证的分支，不会自动创建分支；
历史 `atomgit_hub.upload_folder` 仍只支持默认 `main`。未指定上传 revision 时
仍使用 `main`，不受下载默认分支解析规则影响。

## dataset 上传和建仓是否已经验证？

已经验证。AtomGit 的 HF dataset 创建路由会返回 401，因此 dataset 建仓与上传
都通过当前可用的共享 model 兼容路由完成，用户侧仍使用 dataset 业务类型；
小型文件和约 399 MB 文件均有下载回读 SHA-256 证据。

## 为什么离线测试通过仍可能有远程问题？

mock 只能证明本地参数构造符合测试预期。如果 fake 接受任意 `**kwargs`，它甚至
可能接受真实 HF 方法拒绝的参数。依赖契约测试和受控远程回读缺一不可。

## `atomgit update` 会修改源码 checkout 吗？

不会。editable/source 安装会被拒绝，并提示 `git checkout main`、
`git pull --ff-only`、锁定依赖和 `pip install -e .` 的路径。只有 wheel 安装支持
`atomgit update`。

## 可以用 deploy.sh 发布到 PyPI 吗？

不可以。AtomGit CLI 的唯一官方发布渠道是受保护的手动 GitHub Actions Release
workflow；`deploy.sh` 没有 twine、PyPI token 或远程写路径。详细流程见
[release.md](release.md)。

### 下载续传锁与升级

续传缓存使用操作系统文件锁，同一个远程文件的竞争任务会立即报告已有下载，
不同文件仍可独立下载。进程退出或崩溃后锁自动释放；缓存中的 `.lock` 文件
会保留，它的存在不代表下载仍在运行，不要手动删除正在使用的锁文件。
升级或回滚前先停止旧下载进程，避免 PID 锁版本与系统锁版本同时使用同一缓存。
已有 `.part` 断点和校验规则保持不变，无需清空缓存。

Windows CLI 重定向输出使用 UTF-8；读取日志的程序也应按 UTF-8 解码。

### 大仓库中的单文件下载

显式指定 `--repo-type model` 或 `--repo-type dataset` 时，单文件下载优先查询
目标文件元数据，成功后直接下载，不枚举整个仓库。校验与续传复用此次元数据。
服务不支持所需元数据或返回含义不明确的 404 时保留原有枚举路径；认证失败、
限流和网络错误仍正常报告，不以枚举掩盖。省略类型时保留原有自动识别逻辑。
这一优化减少准备请求，不改变文件本身的网络传输带宽。
