# 上传观测窗口设计草案

状态：已完成方案讨论，尚未实现。本文记录后续开发的已采纳结论，不代表当前
CLI 已提供这些命令或状态文件。

## 目标与边界

为 resumable 大批量上传增加一个独立终端中的只读观测窗口，展示上传速度、
低速检测、连接替换和替换后的改善情况，同时保证观测失败不会阻塞、终止或改变
上传决策。

本方案只旁路复制现有慢速恢复状态，不改变 5 秒采样、30 秒判定窗口、连续三个
低速窗口、收益检查、冷却时间或每对象最多三次替换等上传策略。这里的“替换”是
替换当前对象的 LFS 请求连接，不是重启 CLI 进程；健康 Flow 和其他 worker 继续
上传。

当前已经运行的上传进程没有发布完整速度窗口和内部状态，因此新功能实现后只对
新启动的上传会话生效。开发源码不会热更新或影响已经运行的 Python 上传进程。

## 命令与兼容性

状态功能以 `atomgit upload status` 为入口：

```bash
atomgit upload status
atomgit upload status --watch
atomgit upload status --list
atomgit upload status SESSION_ID
atomgit upload status SESSION_ID --watch
```

各命令的约定如下：

- `atomgit upload status`：一次性显示当前活动会话；没有活动会话时显示最近结束
  的会话，然后退出。
- `atomgit upload status --watch`：每秒刷新默认活动会话；`Ctrl+C` 只关闭观测
  窗口，不给上传进程发送停止信号。
- `atomgit upload status --list`：一次性列出活动会话和保留期内的近期会话，
  用于发现 `SESSION_ID`。这是会话摘要列表，不是 Flow 明细。
- `atomgit upload status SESSION_ID`：一次性显示指定会话的摘要、Flow 最新状态和
  最近事件，包括已经结束的会话。
- `atomgit upload status SESSION_ID --watch`：持续观察指定会话，适合并行存在
  多个上传任务时固定关注一个会话。

必须保持现有位置参数上传语法，并新增等价的显式本地路径参数：

```bash
# 历史语法继续有效
atomgit upload ./data --repo-id user/repo

# 新的明确语法
atomgit upload --path-in-local ./data --repo-id user/repo

# 本地和远端路径形成对称
atomgit upload --path-in-local ./data \
  --path-in-repo datasets/train/ --repo-id user/repo
```

`PATH` 和 `--path-in-local` 都受支持，但同一次调用只能提供一个；同时提供时以
参数冲突退出，不能猜测优先级。新文档优先推荐 `--path-in-local`，旧脚本无需迁移。

裸单词 `status` 保留为状态入口。本地目录确实名为 `status` 时，使用明确路径：

```bash
atomgit upload ./status --repo-id user/repo
atomgit upload --path-in-local status --repo-id user/repo
```

## 数据通路与无干扰原则

观测采用“最新状态覆盖 + 有界关键事件”的双通路：

```text
上传 worker
  ├─ 覆盖 Flow 最新状态槽位
  └─ 追加低频关键事件
           ↓
      非阻塞内存发布器
           ↓
  合并并原子替换本地会话快照
           ↓
  独立 status 进程只读并渲染
```

每个 Flow 只有一个最新状态槽位。速度从 18.2、17.8 变为 0.4 MiB/s 时，旧数值被
覆盖，不为每次采样追加一条无限增长的记录。趋势只保留固定长度的环形数组。

关键事件才进入有界队列，例如进入低速观察、批准替换、冷却开始、新连接开始、
改善验证通过或失败、自动替换停用、完成和失败。每次载荷读取、每个 5 秒速度样本、
重复稳定状态和普通剩余字节变化不进入事件队列。因此这里的“有界事件队列”确实
包含事件类型筛选，但它是在事件产生时分类，不是从一份完整调试日志中事后过滤。

建议最多保留最近 200 条关键事件。容量耗尽时淘汰最旧事件；替换次数、阶段和最终
结论仍保存在 Flow 最新状态及会话累计值中。状态更新按 Flow 覆盖，关键事件低频且
有界，因此不会因观测数据无限增长而占用上传内存。

上传热路径只做非阻塞内存更新。无法立即获得观测锁、发布器繁忙、状态目录不可写或
序列化失败时，允许合并或丢弃可替代的中间显示采样，绝不等待磁盘，也不改变上传
结果。关键计数和阶段使用最新状态兜底。后台发布器最多每秒原子写一次快照；状态
变化可唤醒发布器，空闲时每 2 秒刷新心跳。观测窗口默认每秒重绘。

## 采样、字段与计算

设：

- `b`：一次样本中被网络请求消费的应用层载荷字节；
- `t`：本地有载荷可供消费时的网络节奏等待时间；
- `S`：当前正式速度窗口；
- `O`：Flow 自身稳定基线；
- `P`：稳定同伴基线。

每个 Flow 保存以下最新状态：

### `flow_id`

Flow 注册时分配会话内匿名编号，如 `Flow-01`。它只用于把多次状态更新关联到同一
对象；状态文件不得保存源路径、仓库路径、LFS OID、URL、请求头或 token。

### `sample_speed`

约 5 秒的界面显示速度：

```text
sample_speed = sum(b) / sum(t)
```

例如有效 5.2 秒内消费 52 MiB，显示为 10 MiB/s。它只用于及时反馈，不参与连接
替换判断。

### `window_speed`（即 `current_speed`）

正式的约 30 秒策略速度：

```text
window_speed = 30 秒窗口累计有效载荷字节 / 累计有效等待时间
```

例如累计消费 306 MiB、有效时间 30.6 秒，结果为 10 MiB/s。它是应用层载荷消费
速度，不是整台机器的网卡流量。

### `stable_baseline`

取当前 Flow 最近三个稳定正式窗口的中位数：

```text
O = median(S1, S2, S3)
abs(S2 - S1) <= 0.20 * S1
abs(S3 - S2) <= 0.20 * S2
```

`40, 42, 39 MiB/s` 形成 40 MiB/s 的自身基线；`40, 20, 39 MiB/s` 波动过大，
不形成可靠基线。后续稳定窗口可滚动更新自身基线。

### `peer_baseline`

对候选 Flow 以外的活跃 Flow，在最近三个正式窗口分别计算中位数 `M1..M3`。每个
窗口至少有两个同伴位于该窗口中位数的 70% 到 130% 之间，且 `M1..M3` 相邻变化
不超过 20%，才形成：

```text
P = median(M1, M2, M3)
```

同伴不足或不稳定时显示 `--`，不得制造同伴比较结论。

### `slow_windows`

有可靠同伴基线时，一个正式窗口必须同时满足：

```text
S <= 0.30 * P
S <= 0.50 * O
```

没有同伴基线时使用：

```text
S <= 0.30 * O
```

连续满足时从 `1/3` 增长到 `3/3`；任何不满足窗口归零。`3/3` 只表示成为替换
候选，还需要通过预计收益、冷却、剩余总时限、改善要求和次数上限检查。

### `replacement_count`

只有恢复策略正式批准当前 Flow 的连接替换时加一，显示 `n/3`。网络库正常建立
请求或切换到下一个对象不计入。达到三次或改善验证失败后可能停止自动替换，但上传
仍可继续。

### `remaining_bytes`

界面名称使用“当前请求估计剩余”：

```text
remaining = max(0, 对象总字节 - 服务端已确认 part 字节 - 当前尝试已消费字节)
```

basic PUT 替换后从对象起点重传，该数值可能回升；multipart 保留同一 action 中已获
有效 ETag 的 part，只重试未确认 part。因此它是观测估算值，不承诺单调下降。

### `phase`

由内部状态映射为：`建立基线`、`稳定`、`疑似低速`、`等待替换`、`重连后验证`、
`已恢复`、`自动替换已停用`、`完成`或`失败`。`自动替换已停用`不等于上传停止。

### `updated_at`

记录最后一个有效样本、正式窗口或关键状态变化的时间。界面展示“2 秒前更新”；超过
陈旧阈值后显示“状态可能陈旧”，但不能仅据此宣告上传失败。

### `last_decision`

保存最近一次策略解释，例如“低速窗口不足”“预计收益不足”“等待 60 秒冷却”或
“替换后未达到 2 倍改善”。它用于解释为什么没有重连或为什么停止重连，不替代事件
时间线。

## 趋势图与跨 Flow 比较

每个 Flow 保留最近 12 个正式窗口，即最近约 6 分钟，使用固定长度环形数组。不能按
每条 Flow 自己的历史最大值独立缩放，否则 0.3 MiB/s 和 40 MiB/s 都可能显示成满格，
造成错误的横向印象。

采用“绝对速度 + 相对可靠基线百分比 + 统一百分比刻度”：

```text
reference = peer_baseline（存在时），否则 stable_baseline
ratio = window_speed / reference
```

所有 Flow 的趋势字符使用同一分段：

```text
▁  0%～15%       ▂  15%～30%      ▃  30%～50%
▄  50%～70%      ▅  70%～90%      ▆  90%～110%
▇ 110%～130%     █  >=130%
```

精确 MiB/s 支持绝对速度比较，相对百分比反映每个 Flow 相对健康水平的变化，统一分段
避免各自缩放造成误导。没有可靠 reference 时显示 `--` 和未定标趋势，不把该 Flow
纳入相对排序。

预期的 `--watch` 主界面：

```text
会话 a84f21 | 上传中 | 批次 2/18 | 最近更新 1 秒前
活跃 Flow 3 | 正式窗口速度合计 69.2 MiB/s | 累计替换 1

Flow  5秒速度    30秒速度   相对基线  低速  替换  最近6分钟    状态
01    41.2 MiB/s 40.8 MiB/s 102%      0/3   0/3   ▆▆▆▆▆▆▆▆   稳定
02     0.3 MiB/s  0.4 MiB/s   1%      2/3   0/3   ▆▆▅▄▂▁▁▁   疑似低速
03    28.4 MiB/s 28.0 MiB/s  70%      0/3   1/3   ▆▂▁▃▄▅▅▅   重连后验证

最近事件
14:31:00 Flow-03 已替换当前连接，开始改善验证
14:32:00 Flow-02 持续低速，2/3
```

窄终端可隐藏基线列并缩短趋势，但必须保留精确速度、低速计数、替换计数和阶段。

## 状态表、事件区与会话列表的层级

三者用途和字段不同：

```text
会话摘要
├── Flow 最新状态表：现在怎么样
│   ├── Flow-01
│   ├── Flow-02
│   └── Flow-03
└── 最近事件区：刚才发生了什么
```

Flow 状态表每个 Flow 一行，持续覆盖。事件区按时间顺序展示最近的重要状态变化；两者
在详情和 watch 界面中分区显示。

`atomgit upload status --list` 位于更高层，它列的是上传会话而非 Flow，所以使用
会话摘要字段：

```text
SESSION  状态    开始时间  批次   活跃/峰值Flow  替换  最近更新
a84f21   上传中  14:00     2/18   5/5            1     2秒前
9c117e   成功    09:10     18/18  0/5            2     11:42
```

用户先从列表取得 `SESSION_ID`，再用 `status SESSION_ID` 查看该会话内部的 Flow 状态
和事件。这种层级避免多个会话的所有 Flow 混在同一张表里。

## 快照、保留和安全

建议使用版本化的私有状态目录：

```text
~/.cache/atomgit/upload-observe/v1/<session-id>.json
```

目录权限 `0700`、文件权限 `0600`。发布器写同目录临时文件后原子替换快照，读进程
不会读到半份 JSON。状态不得包含 token、URL、请求头、响应正文、源路径、仓库路径、
仓库名或完整 OID；Flow 仅使用会话内匿名编号。

上传结束时写入成功或失败、开始和结束时间、最终文件/批次统计、累计替换次数、改善
结果和最近事件，默认保留 24 小时。例如上传终端已经关闭后，`atomgit upload status`
仍可显示：

```text
会话: a84f21
结果: 成功
确认完成: 368/368
连接替换: 2 次
替换后改善成功: 2
自动替换停用: 0
```

过期清理由下一次上传命令或 status 命令顺手执行，不启动常驻清理服务。只删除过期
观测快照，绝不触碰源文件、上传投影、HF 续传元数据或远端内容。

## 后续实现验收重点

- 观测开启、关闭、写入失败和队列压力下，上传决策与测试结果必须完全相同。
- `Ctrl+C`、观测进程崩溃和删除快照均不得影响上传进程。
- `PATH` 历史语法、所有现有 upload 参数及帮助行为必须保持兼容。
- 裸 `status` 与 `./status`、绝对路径和 `--path-in-local status` 必须有明确测试。
- 多会话选择、指定会话 watch、陈旧心跳、原子快照、权限、保留期和过期清理需要
  离线回归。
- 快照和错误输出必须通过凭据、URL、路径及 OID 脱敏测试。
- 完整测试和实际上传验证应在当前大批量上传结束后执行；开发可在独立 worktree 中
  进行，避免与运行中的上传争用工作区和测试资源。
