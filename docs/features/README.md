# 特性文档目录

`docs/features/` 是仓库中面向用户和维护者的特性说明目录。以后新增或
调整一个可识别的产品特性，应在这里建立独立的 Markdown 文档；通用开发
流程、架构事实和测试规范仍分别维护在 `docs/development.md`、
`docs/architecture.md` 和 `docs/testing.md`，不在特性文档中重复维护。

## 文档规则

- 每个特性使用一个稳定、可读的英文文件名，例如
  `upload-monitor.md`；文件名一旦被其他文档引用，不要随意改名。
- 文档开头必须写明特性状态：`已实现`、`部分实现`、`设计中`、`已废弃`
  或 `仅方案`。
- 必须明确区分当前源码事实、已验证行为、计划行为和非目标；尚未实现的
  命令、状态文件或接口不能写成当前已提供能力。
- 特性说明至少覆盖：目标与边界、用户入口、核心行为、数据/状态模型、
  失败与安全边界、兼容性约束和验收重点。涉及观测或日志时，还要说明
  采样、刷新、保留和脱敏策略。
- 对外命令、参数、输出或状态含义发生变化时，先更新对应特性文档，再
  同步 `docs/README.md`、用户指南或 CLI 基线；实现任务仍必须遵守
  `.ai/DEVELOPMENT_FLOOR.md` 的能力登记和测试要求。
- 特性文档不能替代实现、测试或 Issue 合同。实现状态以源码和测试为准，
  任务权限与验收证据以 `.ai/TASK.md` 为准。
- 文档中的示例不得包含真实 token、签名 URL、真实请求头、完整 LFS OID
  或其他凭据；示例会话 ID 和路径必须是合成值。
